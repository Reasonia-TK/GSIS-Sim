## 1. 画面の流れ

左の一覧の 6 つの段階を上から順に進める。前の段階が終わっていない段階は、理由を出して押せなくする(戻るのは自由)。各段階の状態(未着手・済・要やり直し)を一覧に記号で出す。前の段階を変えたら、後の段階を「要やり直し」にする(例: 形状を変えたら、境界条件の割り当てを検査し直し、メッシュを捨てる)。

| 段階 | 画面 | 内容 |
|---|---|---|
| 1 | 形状 | STEP・IGES・BREP の読み込み(単位を選ぶ)、または AI モデリング(いまの「モデリング(AI)」の画面を、この段階のタブにする)。**流れの領域の決め方**: 内部流(読み込んだ立体がそのまま流体の領域)/ 外部流(立体を囲む箱を作り、立体を引く。箱の大きさは立体の外接箱の倍数で指定)。面の一覧(番号・面積・重心・法線)と 3D 表示。検査: 閉じた立体が 1 つあること、体積、小さすぎる面・辺の警告 |
| 2 | 設定 | 計算モード(GSIS-PBC / CIS 単独 / NSF のみ(PBC 単独))、気体(プリセットか任意: 分子の質量、μ_ref、T_ref、ω)、基準量(L_ref は形状の代表長さを既定に。基準の温度と圧力は境界条件から既定を出す)、GSIS の設定(n_cis、max_pbc、cfl_pbc、tolerance、上級の設定は折りたたむ)、速度格子(自動 / 手動。§3.3)。導出量(Kn、平均自由行程、VRAM の見積もり)をその場で出す |
| 3 | 境界条件 | 面を 3D 表示でクリックするか一覧で選び、パッチ(名前・種類・値)に割り当てる。割り当てのない面は既定のパッチ(拡散壁、既定の温度)に入れる。種類ごとに要る値だけを入力欄に出す。割り当ては形状の面の番号ではなく、面の幾何(重心・面積・法線)でも照合できる形で保存する(形状を読み直したときに引き継ぐため) |
| 4 | メッシュ | gmsh の四面体(既定)。全体の大きさ、パッチごとの細かさ、なめらかさ(成長率)を指定する。生成は別スレッドで、止められる。品質(セル数、非直交角、歪み、体積比)、パッチの面積(形状の面積との差)、**VRAM の見積もり**(セル数 × 速度点の数)を出し、予算を超えたら警告して実行の段階に進ませない |
| 5 | 実行 | いまの実行の画面を流用する(ソルバーの起動・停止、履歴、GPU のメモリ)。グラフの質量流量はパッチごと。GPU の順番待ち(`runs\.gpu_lock`)に対応する |
| 6 | 結果 | いまの結果の画面を流用する(3D 表示、断面、流線、線上の分布)。管に特化した部分(中心線、Table 1)は例題の管のときだけ出す。追加: パッチごとの質量流量・熱流量・力の表と CSV、壁の表面の分布(圧力・せん断・熱流束。`boundary.vtu`) |

### 1.1 プロジェクト

1 つの計算を「プロジェクト」として 1 つのフォルダにまとめる。開く・保存・名前を付けて保存・最近使ったもの。

```
<project>/
  project.toml          # プロジェクトの設定(段階ごとの入力、版)。GUI が読み書きする
  geometry/             # 読み込んだ CAD の写し、流れの領域の BREP、AI の手順の記録
  boundaries.json       # 面 → パッチの割り当て(面の番号と幾何の両方)
  mesh/<name>.pmesh     # メッシュと品質レポート
  case.toml             # ソルバーに渡すケース(project.toml から作る。手で直さない)
  runs/<日時>/           # 実行の出力(history.csv、summary.json、VTU)
```

- `case.toml` は v1 の書式(`docs/spec.md` §4.6)に、§3 の追加を加えたもの。ソルバーは CLI だけで動く状態を保つ(GUI なしで `gsis-solver run <project>/case.toml` が通る)
- 例題の管は、いまの `cases/tube_vacuum/` からプロジェクトを作る(読み込むだけで、いまのファイルは変えない)

### 1.2 流用と作り直し

## 2. 速度格子と基準量の自動決定

- 基準量: L_ref は形状の代表長さ(既定は外接箱の最小辺。ユーザーが変えられる)。T_ref は境界の温度の最大、p_ref は境界の圧力の最大(圧力の境界がなければ、ユーザーが指定する基準の圧力か、質量流量入口から見積もる)
- 速度格子(自動): 各軸の範囲は、境界の速度の最大 |u|max と最高温度 T_max から ±(|u|max + c √(R T_max))(c = 5、論文の管は 1 の温度で ±8〜10 に相当)。刻み Δξ は最低温度 T_min から Δξ ≤ 0.7 √(R T_min)(論文の管 2/3 に合わせる)。点の数はこの 2 つから決め、偶数にそろえる
- VRAM の見積もり: f(セル数 × 速度点 × 4 バイト)+ 作業領域(チャンク幅から)。予算は `docs/spec.md` §4.4 の方式。超えたら、速度点かセルを減らす案を出す
- 見積もりの式は C++ の `check-case` と Python で同じにし、`check-case --json` の出力で突き合わせる試験を置く

## 3. ソルバーの追加

### 3.1 適応係数付きの壁(Maxwell の壁)

- TOML: `type = "maxwell_wall"`、`temperature`(必須)、`accommodation`(α、0 < α ≤ 1。1 なら `diffuse_wall` と同じ)、`velocity`(任意)
- 運動論側: 反射する分布 = α × 壁の Maxwell 分布 + (1 − α) × 鏡面反射。壁の Maxwell 分布の密度は、壁を通る正味の質量流束が 0 になるように決める
- **鏡面反射と速度格子:** 一般の形状では壁の法線が速度格子の軸にそろわないので、反射した速度は格子点に乗らない。反射した速度での f を速度空間で補間し、補間で生じる質量流束の誤差を、拡散の部分の密度で打ち消して正味の質量流束 0 を保つ。補間の方式(三線形など)と、GPU のメモリと時間への影響は Codex が設計して報告する。法線が軸にそろう面では、補間せずに鏡映の対応表(対称面と同じもの)を使う
- マクロ側(PBC、GSIS の段): 論文の付録 B.2・C.2(拡散壁)を一般化する。メソとマクロで整合する境界フラックス(運動論の分布の半空間のモーメントから作る)を、α の壁でも同じ考え方で作る。導出は設計文書に書く
- 検証: (1) α = 1 で `diffuse_wall` とビット単位か丸め誤差で一致、(2) 平行平板のクエット流と熱伝導を α = 0.5 などで、1 次元の参照ソルバー(`verification/ref1d`。α を足す)と比べる(CIS 単独と GSIS)、(3) 法線が軸にそろわない壁(傾けた平板)で (2) と同じ解になること

### 3.2 質量流量入口

- TOML: `type = "mass_flow_inlet"`、`mass_flow`(kg/s、流入が正)、`temperature`(必須)、`tangential_velocity`(圧力入口と同じ)
- 方式: 圧力入口として扱い、その圧力 p_b を反復の中で、パッチの質量流量が目標に合うよう更新する。運動論の段と PBC の段のどちらで、どう更新するか(更新の式、緩和、収束の判定への組み込み)は Codex が設計して報告する。収束した解で、質量流量が目標の 0.1% 以内に入ること
- 出力: 履歴と summary.json に、その時点の p_b を出す
- 検証: 管 δ=10 の圧力入口の解の質量流量を目標にして解き直し、p_b が p_in に 0.5% 以内で戻ること(小さなメッシュで)

### 3.3 一般の形状で使うための追加

- **四面体メッシュでの頑健性(最初の関門):** いまの検証は管の六面体だけ。四面体の管は既定のリミッタで発散した(`docs/progress.md` フェーズ 2)。正値性のリミッタ(`[kinetic].positivity_limiter`)を検証し、四面体の管 δ=1・10 の GSIS と CIS 単独が、六面体の結果と 1% 以内で合うところまで持っていく。合わなければ原因と案を報告する(ここが通らないと、汎用のアプリは成り立たない)
- `check-case --json`: 導出量、基準量、速度格子(自動のときは決めた値)、VRAM の見積もり、パッチの一覧を JSON で出す(GUI が読む)
- 速度格子の自動: `[velocity_grid] auto = true`(§2 の規則)。手で与えた値があればそれを使う
- 基準量: `[conditions]` に `delta_rp`・`Kn`・`p_ref` のどれか 1 つ(今と同じ)。GUI は `p_ref` を書く
- 出力: summary.json にパッチごとの質量流量・熱流量・力(SI)。穏やかな停止(出力先に `STOP` ができたら、その反復で止めて summary.json と VTU を書く。`docs/gui.md` §8 の要望 1)
- 閉じた領域(圧力の境界がない)の扱いは今のまま(全質量で規格化)

### 3.4 VRAM に乗り切らない場合に RAM へ逃がす(ユーザーの依頼、2026-10-18。まず検討)

分布関数 f が VRAM(予算 約 14 GB)に乗らないとき、f を CPU の RAM(31 GB。OS と GUI の分を除くと 20〜24 GB 程度)に置き、GPU には一部だけを載せて計算する。Codex がまず検討書を書き、統括役とユーザーが方式を決めてから実装する。

検討の出発点(統括役の見立て。推測を含む):
- **速度チャンクの単位で出し入れする案(本命):** いまの CIS は速度点をチャンクに分け、1 回の運動論の反復の中でチャンク同士が独立に処理できる(目標分布と壁の流入密度を反復の初めに固定するため、`docs/spec.md` §3.5)。f を固定したホストのメモリ(pinned)に置き、チャンクを GPU に送る → LU-SGS → 戻す、を CUDA のストリームで重ねる。セルごとのモーメントと境界の半空間の流束は、チャンクごとに足し込む(決まった順序で)。PCIe 5.0 x16 の実効 約 25〜50 GB/s で、管の大きさ(9.3 GB)なら 1 反復に読み書き 18.6 GB で 0.4〜0.8 秒の転送が加わる(いまの 1 反復 0.6〜3.7 秒と同じ桁。重ねれば一部は隠れる)
- 障害になりそうな点: `inner_sweeps` の合間の壁の流入密度の作り直し(`inner_wall_update`)はすべての速度点を要る(チャンクを載せたまま内側の反復を回すと、この更新が反復の終わりにずれる。収束への影響を測る)、離散平衡のニュートン法と GSIS の補正(式 (14))はセルごとにすべての速度点を見る(チャンクごとに分けられるか、もう 1 回の出し入れが要るか)、勾配の作業領域
- 比べる案: (a) Windows の CUDA の統合メモリは WDDM で VRAM を超えて確保できない(と理解している。Codex が公式資料で確かめる)ので、明示的な出し入れにする、(b) f を FP16/BF16 で持つ(メモリ半分。δ が大きいところの $f^S-f$ の精度が心配。`docs/spec.md` §8)、(c) 速度格子を問題に合わせて小さくする(§2 の自動で済む場合が多い)
- 検討書に書くこと: 方式、変えるファイル、VRAM と RAM の使い方、1 反復の時間の見積もり(転送と計算の重なり)、収束への影響、決まった順序の足し算(同じ入力で同じ結果)を保つ方法、試験の方法(小さな問題で、全部 VRAM に載せた場合とビット単位または丸め誤差で一致)、GUI への出し方(VRAM の見積もりで「RAM を使う。遅くなる見込み × 倍」と出す)
